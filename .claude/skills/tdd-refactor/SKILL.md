# tdd-refactor — リファクタリング

`tdd-front-test-outline → tdd-front-test-code → tdd-front-impl → tdd-server-test-outline → tdd-server-test-code → tdd-server-impl → tdd-refactor` の7番目
(最終)。Red→Green の後の Refactor にあたる。振る舞いは変えず、実装を整える。

## 0. 前提の確認

`docs/work/<機能名>.md` を読む。「進捗」の1〜4番目がチェック済みであることを確認する。

**着手前に全層が緑であることを確認する。** 赤が残っている状態でリファクタリングを始めない
(何が既存の不具合で何が自分の変更による退行か区別できなくなる)。

```bash
make db-up
vp run test:all      # ①単体 + 依存方向 / ②結合(実 Postgres) / ③アプリ(画面・ルートのハンドラ)
vp check             # 整形・リント・型
```

**コード内コメントは最小限にする。** リファクタで触れたコードも、読めば分かることを説明する
コメントは書かない。書いてよいのは、コードだけでは伝わらない最重要な意図(トリッキーな回避策の
理由など)と `TODO` コメントだけ。既存の同種コメントを見つけたら、この基準で削ってよい。

## 1. 検出観点

判断の物差しは `docs/design-principles.md`(DRY・SOLID・YAGNI・KISS、においと対処の表、やりすぎの兆候)。
**優先順位は、プロジェクトの規約・アーキテクチャテスト > KISS > YAGNI > DRY > SOLID。** 今回の変更の差分(`git diff main..HEAD`)を、
原則ごとに次の観点で見る:

**層の責務(S・D)** — `CLAUDE.md`「レイヤー構成」と `.claude/rules/architecture.md` に照らして、本来の層からはみ出したコード:
- 最外周(ルートのハンドラ・ページの `loader` / `action`)に残った、データの組み立てロジックや業務ルール判定(→ `core/domain` の純粋関数へ。書き込みなら `core/application` のユースケースへ)
- `domain` に入り込んだ、I/O・`tx` / `db`・時刻の直接参照(→ 値を引数で受け取る形に。`architecture/architecture.test.ts` で機械的に検出できる)
- ユースケースに入り込んだ、`tx` / Drizzle の直接参照(→ ports 経由に。`db/repositories` へ)
- 画面用の読み取りを、ユースケースにしてしまっているもの(→ `db/queries` を直接呼ぶ形へ。YAGNI)
- `void/db` の `db` をハンドラで直接使っている箇所(→ `c.get('tx')`。詰まる原因になる)
- 肥大化した React コンポーネント(複数責務・分岐の増加。`tdd-front-impl` の分割基準を参照)
- ブラウザに配信されるコード(`pages/` `components/`)からのサーバー専用の import(アーキテクチャテストが検出する)

**重複(DRY)** — 「同じ理由で一緒に変わるもの」が複数箇所にあるか:
- **3 か所目**の重複は抽出する(小さな関数・共通コンポーネント・テストの補助)。2 か所なら見送る
- 同じ知識の二重管理(定義元が複数ある)は、定義元を 1 つにする(Valibot スキーマ・権限カタログは `packages/shared`)。不可避なら両方を同じ変更で直す
- 見た目が似ているだけで、変わる理由が別のものは、**共通化しない**

**不要なもの(YAGNI)**:
- 使われていない引数・関数・設定・import・分岐(`grep` で参照元が無いことを確かめて削除する)
- 1 実装しか無く、規約でも要らない抽象
- 先回りの汎用化・拡張点

**単純さ(KISS)**:
- 入れ子の三項演算子・深いネスト(早期 return、変数への切り出し、コンポーネントの分割で浅くする)
- 長い関数・引数が多い関数(責務を分ける、引数をまとめる)
- 意図を追えない巧妙な書き方(明快な書き方に直す)

**拡張と契約(O・L・I)**:
- 種別ごとに増え続ける `if` / `switch`(2 つ目の実装が現れていれば、種別ごとのルール〈関数〉へ)
- 同種の `db` の関数で、戻り値・例外の契約が揃っていないもの
- 使わない値まで持たせている型・引数・props

**クエリ**:
- 重複クエリ、N+1(ループの中の `db` の関数の呼び出し)

**やらないと決める基準**: 規約で揃えている並び(操作ごとに関数を 1 つずつ、など)を崩す共通化、
1 か所でしか使わないもののための抽象化、読みにくくなる・引数が増える整理は、**やらない**。
やらなかったものと、その理由も作業ノートに残す(`docs/design-principles.md`「やりすぎの兆候」)。

## 2. 振る舞いを変えないリファクタは、先に軸をテストで固定する

重複クエリの削除・内部関数の統合などは、**出力が同じなので普通のアサーションでは退行を
検出できない。** 何を守りたいかを決めてテストにしてから着手する:

- **クエリ本数** — 実行された SQL を数える(結合テストで、Drizzle の `logger`〈`logQuery`〉を差し込んだ接続を使うか、
  `SqlExecutor` を包んで数える)→ 対象を実行 → 本数をアサートする
- **発行された SQL・バインド値** — ロック文やヒント句など、消えても振る舞いが変わらないものを固定する

**記録は、テストごとに新しく作る**(モジュールのグローバルに溜めない)。グローバルに溜めると、アサーション失敗時に後始末が
飛ばされて、以降のテストにまで記録が残る。

このテスト自体は「振る舞いを変えないリファクタリング」の成果物であり、リファクタ前に一度実行して、意図通りの値(現状のクエリ本数等)を
示すことを確認してから着手する。

## 3. 1つ直すごとにテストを回す

まとめて複数箇所を直してから通しで確認するのではなく、1 つの切り出し・統合ごとに関連テストを
実行し、都度緑を確認する。

```bash
vp test run <関連するテストのファイル>
vp run -F @club/<app> test tests/<ファイル>
```

## 4. 整形・最終確認

```bash
vp check --fix       # 整形(Oxfmt)・リント(Oxlint)・型
vp run typecheck
vp run test:all      # 退行が無いことの最終確認(依存方向のテストを含む全層)
```

## 5. 作業ノートを更新する

「進捗」の5番目のチェックボックスを付け、判断の理由を短く追記する。**整理したもの(どの原則に照らして、なぜその形にしたか)と、
整理しなかったもの(なぜやらないと決めたか)の両方**を書く。これで作業ノートの5フェーズが完了する。

## 6. GitHub Issueに記録する

`docs/work/README.md`「GitHub Issue への記録」を参照。**1つ切り出し・統合するたび、軸を固定する
テストを書いたとき、想定外の挙動に遭遇したときに都度コメントする**(このステップまで溜めない)。
フェーズ完了時にはさらに、リファクタで整理した内容・判断の理由・起きた問題の総括を1件書く。
