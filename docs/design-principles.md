# 設計原則

実装・リファクタリングの判断の物差し。**優先順位は、プロジェクトの規約・アーキテクチャテスト > KISS > YAGNI > DRY > SOLID。**
規約（`CLAUDE.md`、`.claude/rules/`）と `architecture/architecture.test.ts` が落ちたら、テストを緩めず設計を直す。

## 原則と、このプロジェクトでの意味

| 原則 | 意味 | このプロジェクトでの例 |
|---|---|---|
| KISS | 一番単純で読める形で書く。早期 return でネストを浅く。三項演算子は入れ子にしない | ルートのハンドラは「受け取る → 検証 → `core` / `db` を呼ぶ → 返す」だけ |
| YAGNI | テストと仕様が要求するものだけ作る | 使われない引数・設定・権限キー・汎用化を先回りで足さない |
| DRY | 重複は 2 か所目まで許し、**3 か所目で共通化**。**同じ知識の二重管理**は最初から 1 つにする | Valibot スキーマは `packages/shared` を API とフォームで共用 |
| S | 1 つの関数・コンポーネントは 1 つの責務 | `domain` は判断、`application` は 1 操作の流れ、`db` はクエリ、最外周は受け口 |
| O | 分岐を書き換え続けず、規約のある所は**追加**で拡張（2 つ目が現れてから） | 新しい割引は、割引ルールを 1 つ足す（既存を書き換えない） |
| L | 実装は契約（戻り値・例外）を守る | `db` の関数は「見つからなければ null か例外」を統一 |
| I | 小さな interface・props。使わない値を持たせない | 大きなオブジェクトを丸ごと下へ流さない |
| D | 内側は外側を知らない（依存性の逆転） | `core` は Void / DB / Hono に依存せず、`db` が `core` の ports を実装する（`architecture.test.ts` が強制） |

## においと対処

| におい | 対処 |
|---|---|
| ハンドラ・loader に業務ルールの判定が残っている | `core/domain` の純粋関数へ（書き込みなら、`core/application` のユースケースへ） |
| `domain` が I/O や時刻を直接触る | 値を引数で受け取る形にする。I/O は `application`（ports 経由）と最外周へ |
| 同じ塊が 3 か所目に出た | 小さな関数・コンポーネントへ抽出 |
| 入れ子の三項演算子・深いネスト | 早期 return、変数への切り出し、分割 |
| 種別ごとに増え続ける `if` / `switch` | 2 つ目の実装が現れていれば、種別ごとのルール（関数）へ |
| 使われていない引数・export・import | `grep` で参照元が無いことを確かめて削除 |
| 重複クエリ・N+1 | クエリ本数をテストで固定してから整理 |

## やりすぎの兆候（やらないと決める基準）

- 規約で揃えている並び（操作ごとに関数を 1 つ、など）を崩す共通化
- 1 か所でしか使わないもののための抽象化
- 読みにくくなる整理・引数が増える整理
- 見た目が似ているだけで、変わる理由が別のものの共通化

やらなかったものは、その理由を作業ノートに残す。
