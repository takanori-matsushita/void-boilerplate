# commit — 変更をコミットする

作業中の変更を、1つの論理的なまとまりごとにコミットする。**push・PR作成・amend・force は、ユーザーが
明示的に頼んだときだけ**(このスキルの範囲外)。唯一の例外は、`tdd-front-test-outline` が、最初のコミットの後の
push と draft PR の作成を指示している場合で、その手順に従う(それ以外のコミットでは push しない)。

## 1. 状況を確認する

```bash
git status --short
git branch --show-current
git diff --stat            # 未ステージ
git diff --cached --stat   # ステージ済み
git log --format=%s -10    # 直近の書式
```

**変更の中身は、ステージ前に必ず読む**(`git diff <ファイル>`)。読んでいない変更をコミットしない。

## 2. ブランチを確認する

**デフォルトブランチ(`main`)には直接コミットしない。** `main` にいたら、先にブランチを切る:

```bash
git switch -c <種別>/<Issue番号>-<英語のスラッグ>     # 例: feature/60-activity-master-delete
```

- 種別: 機能は `feature/`、修正は `fix/`、スキルや設定などは `chore/`、ドキュメントは `docs/`
- Issue 番号は、作業ノート(`docs/work/<機能名>.md` の「対象」)・直近のコミット・会話から探す。分からなければユーザーに聞く
- すでに作業ブランチにいるなら、そのまま使う

## 3. ステージする対象を選ぶ

**`git add -A` / `git add .` は使わない。** 今回の作業に関係するファイルを、パスで指定して `git add` する。

- 含めない: `.env` や認証情報、ビルド成果物(`dist/` `.void/` `.cloudflare/`。`.gitignore` 済み)、アプリ直下の `void.lock.json`(作業用コピー。
  コミットするのは `deploy/<env>/<app>/void.lock.json`)、`.claude/tmp/`(スクショ置き場)、スクラッチ用のファイル、今回と無関係な変更
- 関係の有無が分からない変更が混ざっていたら、**コミットせずにユーザーに聞く**
- 論理的に別のものは**コミットを分ける**。TDD のフェーズなら、テスト(`[test]`)と実装(`[add]`)、
  リファクタ(`[refactor]`)、レビュー対応(`[fix]`)は別のコミットにする。作業ノート(`docs/work/*.md`)は、
  そのフェーズのコミットに含める

## 4. コミットメッセージを書く

```
[種別]#Issue番号 日本語の要約(何をしたか)

- 変更の要点を箇条書きで(何を・なぜ)
- ...

<帰属行>
```

- **種別**: `[add]`(機能の追加)・`[fix]`(不具合・レビュー対応)・`[refactor]`(振る舞いを変えない整理)・
  `[test]`(テストの追加)・`[docs]`(文書)・`[chore]`(スキル・設定など)。過去の `[feat]` `[update]` `[infra]` は新規に使わない
- **`#Issue番号`**: 無ければ付けない(推測で付けない)
- 1行目は簡潔に。書き方は直近のログ(`git log --format=%s -10`)に合わせる
- 文面は日本語。コード識別子はそのまま
- **帰属行**: このセッションのシステムリマインダーで指定された帰属行(`Co-Authored-By:` など)を、そのまま末尾に付ける。
  指定が無ければ付けない

```bash
git commit -q -F - <<'MSG'
[add]#NN …

- …

Co-Authored-By: …
MSG
```

## 5. pre-commit フックの扱い

フックは Lefthook(`lefthook.yml`。**ホストで動く**)で、ステージされたコード(`*.ts` `*.tsx` `*.mts` `*.mjs`)を `vp check` で検査する。
**ファイルは書き換えない**。違反があればコミットが止まるので、`vp check --fix`(または `make fix`)で直し、ステージし直す。
`vp install`(ホスト)の `prepare` で自動的に有効になる(`.git/hooks/pre-commit` があれば有効)。有効でなければ、コミットの前に `vp check` を手で実行する。

- フックは整形しない。違反で止まったら、直してステージし直す
- フックが**失敗**したら、原因を直して**新しいコミットを作り直す**。`--no-verify` で飛ばさない。`--amend` もしない
- コミットの前に、関係するテスト(`vp run test:unit` など。`CLAUDE.md`「開発の進め方」)が通ることも確認する

## 6. 結果を報告する

```bash
git log --oneline -1
git status --short
```

次を簡潔に伝える: コミットのハッシュと1行目、ブランチ、含めたファイル数と主なファイル、作業ツリーが
クリーンかどうか。**push と PR 作成はしていない**ことと、必要なら頼めることを添える。

複数のコミットに分けた場合は、全部を一覧で伝える。
