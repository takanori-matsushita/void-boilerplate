# 権限モデル（設計）

grilling（2026-11-28）で確定した内容。実装は `packages/shared`（権限カタログ・標準ロール）、`packages/core/src/domain`（認可の純粋関数）、各アプリの最外周（`can` の呼び出し）。
決済（Stripe）の方針は `CLAUDE.md`「Stripe」。会員・請求の設計（きょうだい・請求先）は、別の grilling で決める（下の「未決事項」）。

## 1. ユーザーと役割

| 項目 | 決定 |
|---|---|
| 管理画面のユーザー | スタッフ（Better Auth の organization のメンバー）。複数クラブに所属でき、アクティブな組織を切り替える |
| 標準ロール | **運営者**（オーナーを統合）・**事務**・**コーチ**。コードで定義し、削除・編集できない（コピーして使う） |
| カスタムロール | クラブが作れる。**1 クラブ 10 個まで**。DB（Better Auth の `organizationRole`、`dynamicAccessControl`）に保存 |
| ロールの数 | **1 人 1 ロール** |
| 自社（プラットフォーム）のサポート | クラブのデータを見ない。見る必要が出たら、期限・理由・監査ログつきで別途設計する |
| ログイン | メール + パスワード。**運営者は 2 要素認証（TOTP）を必須** |
| 招待 | **期限つき・1 回限りの招待リンク**（ロール・拠点を持つ）を、LINE などで共有する。メール基盤は入れない |
| クラブ（テナント）の作成 | 自社が作る（招待制）。`provisionTenant` を、入口に依存しないユースケースにして、将来のセルフサービスに備える |

### 昇格の防止
1. ロール・メンバーの管理（`staff:manage`）は、標準では運営者だけ。
2. **自分が持たない権限を含むロールは、作れない**（自分の権限の範囲まで）。
3. **最後の運営者は、削除・降格できない**。
4. 標準ロールは編集・削除できない（コピーして使う）。

## 2. 権限カタログ

`リソース : 操作`。`packages/shared/src/permissions.ts` が正本。カスタムロールが選べる権限は、これだけ（Valibot の列挙で検証する）。

| リソース | 操作 |
|---|---|
| `member`（会員） | `view`、`view_pii`（生年月日・保護者の連絡先）、`create`、`update`、`change_status` |
| `invoice`（請求） | `view`、`create`、`record_payment`（入金消込）、`void`（取消）、`refund`（返金） |
| `payment_account`（入金先） | `view`、`manage`（Stripe の方式に依存しない名前） |
| `message`（配信・返信） | `view`、`send`、`reply` |
| `schedule`（日程・出欠・振替） | `view`、`manage`、`attendance` |
| `event`（大会・エントリー） | `view`、`manage` |
| `master`（会場・クラス・料金・種目・コーチ） | `view`、`manage` |
| `staff`（メンバー・ロール・拠点の割り当て） | `view`、`manage` |

## 3. データの範囲（拠点）

- **クラブ間の分離は RLS（`tenant_id`）で DB が強制する**。`tenant` / `site` を含む、すべてのテーブルに RLS がある（`schema.integration.test.ts` が検出する）。
- **同じクラブの中の、拠点の絞り込みは、アプリ側の認可**で行う（RLS ではない）。`queries/` の共通の仕組みで、絞り込みの条件を付け忘れにくくする。拠点を絞ったコーチのテストで、他拠点が見えないことを確認する。DB での二重の防御（`app.site_ids`）は、必要になったら足す。
- 絞り込みは、**メンバーごと**に設定する（ロールと独立）。
  - 「全拠点」はフラグで持つ（運営者・事務の既定）。新しい拠点は、自動で見える。
  - 絞り込んだメンバー（コーチの既定）は、拠点を列挙する。新しい拠点は、自動では見えない。0 件なら、何も見えない。
- 拠点と会場は**同じもの**。会員はクラスに所属し、クラスが拠点に属する（クラス経由で、複数の拠点にまたがれる）。
- 絞り込みは**拠点まで**。クラス単位の絞り込みは、見送る（必要になったら、メンバーごとの「担当クラス」を足す）。
- 範囲外のリソースは **404**、機能の権限がないときは **403**。画面は、権限のない機能のメニューを非表示にする（`loader` が権限の真偽値を渡す）。

## 4. マスタの「コーチ」と、スタッフ

2 つの別のもの。

| | コーチ（マスタ） | スタッフ（ログインするユーザー） |
|---|---|---|
| 何か | 練習の担当者として、スケジュールに載せる人 | 管理画面にログインする人（ロール・拠点を持つ） |
| ログイン | 不要 | 必要 |
| 持つ情報 | 名前、表示用のプロフィール、担当できるクラス | メールアドレス、ロール、見られる拠点 |

- コーチのマスタに、任意でスタッフを紐づける（`coach.staff_member_id`、nullable）。コーチ 1 人にスタッフ最大 1 人、逆も 1 人。同じクラブの中だけ。
- マスタ画面から「ログインを招待」すると、ロール・拠点を指定した招待リンクができ、登録されると紐づく。
- スタッフが外れても、コーチのマスタは残る（`staff_member_id` が空になるだけ。過去の日程の担当は残る）。コーチのマスタは、物理削除せず、無効化（アーカイブ）する。
- 2 つのクラブを掛け持つコーチは、クラブごとに別のコーチのマスタを持ち、同じアカウントが 2 つのクラブに所属する。
- **「担当拠点」の出どころは、スタッフの拠点の設定だけ**。コーチのマスタの「担当できるクラス」は、スケジュールの表示と選択のためで、見られる範囲には影響しない。

## 5. 保護者

- ロールではなく、**関係**（`guardian_member`）で決まる。自分の子ども（招待コード・QR で紐づけた会員）だけを扱う。
- 1 人の保護者に複数の子ども（兄弟）、1 人の子どもに複数の保護者を、多対多で紐づけられる。保護者の間で、権限に差は付けない。
- 複数クラブを、1 つの LINE アカウントで扱える（最初に、クラブを選ぶ）。

## 6. 認可の実装方針

- 権限のチェックは、**ユースケースの入口**（`authorize(ctx, 'invoice:void', { siteId })`）。拠点の絞り込みは、クエリの条件（`siteScope(ctx)`）で効かせる。
- 認可の判断は、`packages/core/src/domain` の**純粋関数**（I/O なし）。権限のセットと拠点の範囲を持つ `AuthContext` を、最外周が作って渡す。
- 監査ログ: ロール・拠点の付与、入金先の変更、請求の取消・返金、退会処理を、共通のテーブル 1 つに記録する（誰・いつ・何・対象・変更前後）。個人情報の閲覧は、最初は記録しない。
