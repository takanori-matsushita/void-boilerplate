# tdd-front-test-outline — 画面のテストのアウトライン作成

`tdd-front-test-outline → tdd-front-test-code → tdd-front-impl → tdd-server-test-outline → tdd-server-test-code → tdd-server-impl → tdd-refactor` の1番目。
このスキルは**仕様を確定し、アウトライン(`it.todo`)を作ってユーザーの確認を取るところまで**。
テストのロジック(Arrange/Act/Assert)は書かない — それは `tdd-front-test-code` の仕事。実装も書かない。

「画面」= Void Pages(`apps/<app>/pages/`。React、SSR なし)。進め方の全体規約は `CLAUDE.md`「レイヤー構成」「開発の進め方」、
テスト方針は `.claude/rules/testing.md` を前提知識として読むこと。ここには**手順**だけを書く。

## 0. ブランチを切り、作業ノートを開く

### ブランチを切る(最初に)

この機能の作業を始める最初のコマンドなので、**他の作業をする前にブランチを用意する**。

1. **Issue 番号を確認する**(起動時の引数、例: `/tdd-front-test-outline #60`)。無ければユーザーに聞く(推測しない)
2. **今のブランチを見る**: `git branch --show-current`
   - `main` なら、最新にして作業ブランチを切る:
     ```bash
     git status --short                       # 未コミットの変更が無いこと(あれば、ユーザーに確認する)
     git switch main && git pull --ff-only    # リモートがまだ無い場合は pull を飛ばす
     git switch -c feature/<Issue番号>-<英語のスラッグ>     # 例: feature/60-class-master
     ```
   - すでにその機能の作業ブランチにいるなら、そのまま使う(再開)。**無関係なブランチなら、止めてユーザーに確認する**
3. `<機能名>`(下の作業ノートのファイル名、英語のスラッグ)と、ブランチ名のスラッグは揃える

### 作業ノートを開く

`docs/work/<機能名>.md` を探す。無ければ `docs/work/README.md` のテンプレートで新規作成する
(`<機能名>` はユーザーに確認するか、対象の URL セグメントから決める)。**対象のアプリ(`apps/admin` か `apps/liff`)も、ここで決めて書く。**

## 1. grilling で画面仕様を詰める

Skill ツールで `grilling` を起動し、frontier が空になるまで次を確定させる:

- **対象のアプリと URL**(Void はファイルパスが URL: `apps/<app>/pages/<path>/index.tsx`)
- **主な利用端末**(スマホ / PC)と、**幅によって操作や情報の構造が変わる所**(表 → カード、ダイアログ → シート など。ある場合は
  `tdd-front-impl` が、レスポンシブか専用のデザインかを判断する材料になる)
- 表示項目(一覧 / 詳細 / 作成 / 編集のどれを持つか、各画面の項目)
- 権限による出し分け(ナビを消すか、アクションを無効化して理由を出すか。権限は `loader` が真偽値で渡す形を基本とする)
- 空状態(データ 0 件の表示)
- エラー表示(バリデーションエラー・サーバーエラーの出し方)
- **ローダーの props の型**(`loader` の戻り値。ページは `InferProps` で型を受け取る。ここがフロントとサーバーの境界の契約になる ──
  曖昧なまま次のフェーズへ進まない)
- フォームの送信(`action`)を持つなら、送る値とエラーの返し方(`packages/shared` の Valibot スキーマを共用する)

結論を作業ノートの「決定事項(grillingで確定)」の該当節(画面仕様 / ローダーの props 契約)へ書き、ユーザーに確認を取る。
「未決事項」が残っていたら埋まるまで進めない。

## 2. どの層のテストかを振り分ける

`.claude/rules/testing.md`「層の使い分け」に従う。**このスキルが書くのは③(コンポーネント。`apps/<app>/tests/pages/**/*.test.tsx`)だけ。**
「HTTP の応答・DB の状態・認可・RLS」はサーバー側(①②と API。`tdd-server-test-outline` / `-code` の担当)なので、そちらへ回す判断を
したら、作業ノートの「検証を置く層の割り振り」に書き残す。実ブラウザでしか観測できないもの(④ E2E)は最小限に絞り、同様に書き残す。

**テストファイルは、`pages/` `routes/` の中に置かない**(ルートとして扱われる。`architecture/architecture.test.ts` が検出する)。
`apps/<app>/tests/pages/<ページ>.test.tsx` に置く(手本: `apps/admin/tests/pages/index.test.tsx`)。

## 3. アウトラインを生成する(テストロジックはまだ書かない)

`describe('文脈', () => { ... })` の階層構造と `it.todo('〜の時、〜であること')` だけを並べる(`vite-plus/test` から import する)。
テスト名はそれ自体が仕様書として読めるように、振る舞いが明確にわかる日本語で書く。
Arrange/Act/Assert の中身はこの段階では書かない。ユーザーに確認を取ってから次へ。

### ユーザーへの見せ方(スマホなど、遠隔の端末からでも読めるように)

ユーザーは端末から遠隔で操作していることがある。**ローカルのファイルパスは端末から開けない**ので、確認を求める前に、
次の2つを**両方**行う:

1. **アウトラインの一覧を、会話にコードブロックで貼る。** ファイル全文ではなく、`describe` の階層とテスト名だけのツリー
   (1行1ケース。件数も添える)。`grep -nE "describe\(|it\.todo" <ファイル>` の出力を整形すればよい。意図を示すコメントは、
   必要なケースにだけ添える
2. **テストファイルそのものを `SendUserFile` で送る**(`display: "attach"`、`status: "normal"`、caption に件数)。
   複数ファイルは1回の呼び出しにまとめる。`SendUserFile` が未ロードなら、先に `ToolSearch` で `select:SendUserFile` を読み込む

修正の依頼を反映したら、変更したファイルだけ送り直し、変更点を短く伝える。

## 4. 作業ノートへ記録して引き継ぐ

`tdd-front-test-code` は別のセッションで起動されうるため、アウトラインの所在と確認状況を**会話ではなく作業ノート**に書く。
`docs/work/<機能名>.md` に次の節を足す(ユーザーが確認した後に「確認済み」にする):

```markdown
### テストのアウトライン(`tdd-front-test-outline`、YYYY-MM-DD)

- ファイル: <パスと件数>(`it.todo` のみ。ロジックは未実装)
- 確認状況: 確認済み / 確認待ち(<修正依頼があれば内容>)
- 画面仕様・ローダーの props 契約の決定事項: 上の「決定事項」の各節に記載済み
```

「進捗」のチェックボックスは**ここでは付けない**(付けるのは `tdd-front-test-code` がRedを目視した後)。

### コミットして、draft PR を作る(アウトラインの確認が取れたら)

**GitHub は、`main` との差分(コミット)が無いブランチでは PR を作れない。** そのため draft PR は、ブランチを切った
直後ではなく、**アウトラインをユーザーが確認した後の最初のコミット**のあとに作る。

1. **コミットする**(`commit` スキルの手順に従う: 書式・ステージ対象・pre-commit フック)。含めるのは、アウトラインのテスト
   ファイルと作業ノート。メッセージは `[test]#<Issue番号> <機能名>の画面のテストのアウトラインを追加する`
2. **`/pr --draft` の手順で、push と draft PR の作成を行う**(Skill ツールで `pr` を引数 `--draft` で起動する。
   push・既存 PR の確認・タイトル・本文は `pr` スキルが決める。ここでは書式を持たない)
   - draft の本文には「進捗」節が入る。作業ノートの「進捗」から作られるので、ここでは何も書かない
   - メディアは、この段階では添付しない(`--draft` は撮影の工程を飛ばす)
3. **PR の URL を、ユーザーに伝える**(端末から開けるように)。作業ノートの「対象」節と、GitHub Issue のコメントにも書く
4. **`gh pr ready`(draft の解除)はしない**。以降のフェーズのコミットを push するかも、ユーザーの指示に従う(`commit` は push しない)。
   本文の更新と Ready 化は、実装が終わった後に、ユーザーが `/pr` / `/pr --ready` と指示したときに行う

`gh` が使えない・リモート(`origin`)が無い・push や PR 作成に失敗したら、**エラーを報告して続ける**(アウトラインの作業は止めない。
`pr` スキルの「失敗したら止める」より、こちらを優先する)。

次は `tdd-front-test-code` を明示的に起動する。

## 5. GitHub Issueに記録する

`docs/work/README.md`「GitHub Issue への記録」を参照。**grilling での仕様確定・判断に迷った点・想定外の挙動に
遭遇するたびに都度コメントする**(このステップまで溜めない)。アウトラインの確認が取れたら、詰めた仕様と
アウトラインの構成(ファイルと件数)を1件書く。フェーズの総括(Red目視を含む)は `tdd-front-test-code` が書く。
