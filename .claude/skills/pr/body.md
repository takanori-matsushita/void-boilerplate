# 本文の組み立て(`/pr` の工程 4)

書式の正本は `.github/PULL_REQUEST_TEMPLATE.md`。**必ずそれを読んで、その節構成で埋める**(節を足したり減らしたりしない。
テンプレートを直したら、このスキルは何も変えずに追従する)。

## タイトル

`[種別]#Issue番号 日本語の要約`(`/commit` と同じ書式)。

- 種別: ブランチの接頭辞から決める — `feature/` → `[add]`、`fix/` → `[fix]`、`chore/` → `[chore]`、`docs/` → `[docs]`
- Issue 番号: ブランチ名(`feature/92-...` の `92`)→ 作業ノートの「対象」→ 会話、の順に探す。**無ければ付けない**
  (`[chore]` / `[docs]` は番号なしでよい。`feature/` で番号が取れないときは、推測せずユーザーに聞く)
- 要約: 作業ノートの題と `git log main..HEAD --format=%s` から。`draft` の間は「〇〇を実装する」でよい
- **既に PR があるときは、タイトルを書き換えない**(手で直されていることがある)。ユーザーが頼んだときだけ変える

## 材料

| 節 | 材料 |
|---|---|
| 概要 | 作業ノート(`docs/work/<機能名>.md`)の「対象」「決定事項」、`git log main..HEAD`。`Closes #N`(Issue 番号があるときだけ) |
| 進捗 | 作業ノートの「進捗」のチェックボックス。作業ノートが無ければ節ごと省く |
| 変更内容 | `git diff main...HEAD --stat` を層ごとにまとめる(画面 `apps/*/pages` `components` / サーバー `apps/*/routes` `packages/*` / DB `apps/admin/db/migrations` / デプロイ・CI `deploy/` `.github/` / docs・設定)。該当しない層は書かない |
| テスト | `git diff main...HEAD --name-only` のうち `*.test.ts` `*.test.tsx` `*.integration.test.ts` と `architecture/`。追加・変更の一覧と件数。**Red を目視した旨は、作業ノートの記録に書いてあるときだけ**書く(無いのに書かない) |
| 確認方法 | 画面の変更があるときだけ。開発サーバーの URL(管理画面 `http://localhost:5301/...`、LIFF `http://localhost:5302/...`)と、ログイン情報の参照先(認証の導入後は、シードで作るサンプルテナントの管理者。作業ノートに書く)、手順。`docs/work/<機能名>.capture.mjs` があれば、その操作の流れを文章にする。画面の変更が無ければ「画面の変更なし」と書く |
| リリース時の注意 | **DB**: `git diff main...HEAD --name-only` の `apps/admin/db/migrations/**`。`tenant_id` を持つテーブルを作っているのに、そのマイグレーションの末尾に `tenantTableRlsSql` の SQL(`ENABLE ROW LEVEL SECURITY` とポリシー)が無ければ、その旨を書く(`grep -n "ROW LEVEL SECURITY" <該当のマイグレーション>`)。マイグレーションは `deploy.yml` の `migrate` ジョブ(管理用ロール)で、デプロイの前に適用されることも書く。**権限**: `packages/shared` の権限カタログに差分があれば、追加・変更したキーを書く。**環境変数・シークレット**: `apps/*/env.ts` の差分(新しいキーは、環境ごとに `void secret put` か `provision` ワークフローの再実行が要る)。**インフラ**: `queues/` `crons/` の追加(Queue 名は `<Worker名>-<キュー名>`)、`void.config.ts`、`deploy/**/void.lock.json` の差分。手動コマンドの要否は差分から判断できないので、**ユーザーに聞く**。どれも無ければ「なし」と書く |
| レビューしてほしい点・やらなかったこと | 作業ノートの「未決事項」「決定事項」のうち、判断に迷ったもの、YAGNI で見送ったもの、後続 Issue に回したもの。無ければ「なし」 |
| メディア | `media.md` の結果。画面の変更が無ければ「画面の変更なし」と書く |
| 関連 | Issue、作業ノート、関連 PR(`gh pr list` で同じ Issue のものがあれば) |

**事実だけを書く。** 実行していないテストを「通った」と書かない、撮っていない画面を載せない、作業ノートに無い判断を足さない。
分からない節は `(未定)` と書く(`--ready` の条件で止まる)。

## マーカーと更新の仕方

本文は、`<!-- pr:start -->` 〜 `<!-- pr:end -->` の**内側が `/pr` の管理範囲**。毎回、**内側を全節まるごと作り直す**
(一部だけ直すと、古い記述が残る)。**外側は触らない**(人が手で足した補足が入っている)。

1. 本文を書くファイルは、**セッションのスクラッチ領域**に作る(リポジトリに残さない)
2. **PR が無いとき**(新規作成): マーカーで囲んだ本文を作り、その後ろに帰属行を付ける。
   ```bash
   gh pr create --base main --head <ブランチ> --title "<タイトル>" --body-file <本文> [--draft]
   ```
   作る前に `gh pr list --head <ブランチ> --state open --json url,number` で、既にないかを確認する
3. **PR があるとき**(更新): 現在の本文を取り、マーカーの内側だけを差し替える。
   ```bash
   gh pr view <番号> --json body --jq .body > <現在の本文>
   ```
   - マーカーがある → 内側だけ差し替える(外側はそのまま)
   - **マーカーが無い**(手で作られた PR) → 既存の本文は消さず、マーカーで囲んだ新しい本文を**先頭に**足し、
     元の本文は「元の本文」という見出しの下にそのまま残す。その旨をユーザーに伝える
   ```bash
   gh pr edit <番号> --body-file <新しい本文>
   ```
4. **帰属行**: このセッションのシステムリマインダーで指定された PR 用の帰属行(`🤖 Generated with ...` とセッションの URL)を、
   **マーカーの外側の末尾**に付ける。既にあれば足さない。指定が無ければ付けない
5. 更新したら、`gh pr view <番号> --json body --jq .body` で、マーカーの内側が意図どおりか・外側が変わっていないかを確認する
